🤖 RPABotCore & BotState Lifecycle

This documentation explains the relationship between RPABotCore (the RPA automation engine) and BotState (the state management system). Understanding their lifecycle and interactions is crucial for maintaining and extending the ParkBot system.

📋 Overview

🏃 RPABotCore

The RPA (Robotic Process Automation) engine that:

  • Controls browser automation via Playwright
  • Runs message processing loop in a background thread
  • Matches messages against patterns
  • Executes reactions (likes) on matched messages
  • Maintains _running flag for loop control

💾 BotState

The state management singleton that:

  • Tracks seen message IDs per group (prevents reprocessing)
  • Tracks reacted message IDs per group (prevents duplicate reactions)
  • Maintains runtime statistics (match_count, reaction_count, fail_count)
  • Persists state to state.json automatically
  • Provides thread-safe operations with locks
  • Calculates uptime from start_time

🔄 Lifecycle Phases

Phase 1: Initialization

When the App starts, both components are initialized:

sequenceDiagram participant App as App (GUI) participant RPA as RPABotCore participant State as BotState participant File as state.json App->>State: new BotState() State->>File: _load_state() (if exists) File-->>State: Restore seen_ids, reacted_ids State-->>App: BotState instance App->>RPA: new RPABotCore(monitor_settings, internal_settings, state) RPA->>RPA: Create PatternMatcher with patterns RPA->>RPA: Initialize _running = False RPA-->>App: RPABotCore instance
Key Points:
  • BotState loads persisted data from state.json on initialization
  • RPABotCore receives BotState as a dependency (dependency injection pattern)
  • RPABotCore stores reference to BotState in self.state
  • PatternMatcher is created with patterns from MonitorSettings

Phase 2: Bot Start

When user clicks "Start", the bot begins execution:

fail_count, start_time, recent_logs App->>State: is_running = True App->>State: start_time = time.time() App->>RPA: start() RPA->>RPA: _running = True RPA->>Thread: Create new Thread(target=run_async) Thread->>Thread: run_async() Note over Thread: Browser setup & navigation
happen in background

Data Flow at Start:

  1. App calls BotState.reset() to clear runtime statistics
  2. App sets BotState.is_running = True
  3. App sets BotState.start_time for uptime calculation
  4. App calls RPABotCore.start() which spawns background thread
  5. RPABotCore sets _running = True (internal loop flag)

Phase 3: Message Processing Loop

The core interaction pattern during message processing:

sequenceDiagram participant Thread as Background Thread participant RPA as RPABotCore participant State as BotState participant File as state.json participant Page as Feishu Page loop While _running = True Thread->>RPA: _get_messages(group) RPA->>Page: Query message elements Page-->>RPA: Message wrappers loop For each message RPA->>State: is_seen(group, msg_id) State-->>RPA: False (not seen) RPA->>State: mark_seen(group, msg_id) State->>State: Add to seen_ids set State->>File: _save_state() (persist) RPA->>RPA: matcher.matches(text) alt Message matches pattern RPA->>State: is_reacted(group, msg_id) State-->>RPA: False (not reacted) RPA->>State: match_count += 1 RPA->>RPA: _react(element) alt Reaction success RPA->>State: reaction_count += 1 RPA->>State: mark_reacted(group, msg_id) State->>State: Add to reacted_ids set State->>File: _save_state() (persist) else Reaction failed RPA->>State: fail_count += 1 end end end RPA->>State: update_last_checked_ids(group, ids) State->>File: _save_state() (persist) Thread->>Thread: asyncio.sleep(check_interval) end
Critical Interaction Pattern:
  • Check before processing: Always call is_seen() first to avoid duplicate processing
  • Mark immediately: Call mark_seen() right after to prevent race conditions
  • Persist on change: Every state change triggers _save_state() to disk
  • Check before react: Call is_reacted() to avoid duplicate reactions
  • Thread-safe: All BotState operations use self._lock for thread safety

Phase 4: Bot Stop

When user clicks "Stop" or an error occurs:

sequenceDiagram participant User as User participant App as App participant RPA as RPABotCore participant State as BotState participant Thread as Background Thread alt User Stops Bot User->>App: Click Stop Button App->>RPA: stop() RPA->>RPA: _running = False else Browser Closed/Error Thread->>RPA: Browser exception RPA->>RPA: _running = False RPA->>RPA: log("浏览器已关闭") end Thread->>RPA: Loop exits (_running = False) RPA->>State: is_running = False RPA->>RPA: stop_callback() RPA->>RPA: _cleanup() Note over RPA: Close browser context & playwright

Stop Sequence:

  1. User calls RPABotCore.stop() or exception sets _running = False
  2. Background loop detects _running = False and exits
  3. RPABotCore sets BotState.is_running = False
  4. RPABotCore calls stop_callback (notifies UI)
  5. RPABotCore calls _cleanup() to close browser resources

Phase 5: Statistics Access

UI queries runtime statistics (runs on main thread):

📊 State Attributes Reference

Attribute Type Persisted Description
_group_states[group]["seen_ids"] Set[str] ✅ Yes Message IDs that have been processed
_group_states[group]["reacted_ids"] Set[str] ✅ Yes Message IDs that have been reacted to
_group_states[group]["last_checked_ids"] List[str] ✅ Yes IDs from the most recent check
match_count int ❌ No Runtime: Messages that matched patterns
reaction_count int ❌ No Runtime: Successful reactions
fail_count int ❌ No Runtime: Failed reactions
start_time float ❌ No Runtime: Timestamp when bot started
is_running bool ❌ No Runtime: Current bot state

📝 Persistence Strategy

Persisted to state.json: seen_ids, reacted_ids, last_checked_ids, last_check_time

Runtime only: Statistics counters (match_count, reaction_count, fail_count), start_time, is_running

Why this split? Persisted data survives restarts (prevent duplicate processing), while runtime statistics are reset each session.

🔧 Key Methods Reference

BotState Methods

Check if message was already processed

Mark message as processed & persist

is_reacted(group, msg_id) → bool

Check if already reacted to message

mark_reacted(group, msg_id)

Mark as reacted & persist

update_last_checked_ids(group, ids)

Update recent check IDs & persist

reset()

Clear all runtime statistics (not persisted data)

RPABotCore State Interactions

_run_loop()

Main loop: Checks state.is_seen, calls state.mark_seen, updates counters

_get_messages(group)

Filters out seen messages via state.is_seen()

_react(element)

On success: increments reaction_count, calls mark_reacted

⚠️ Thread Safety Considerations

Important: RPABotCore runs in a background thread, while UI queries BotState from the main thread.

BotState uses threading.Lock() internally to ensure:
  • Concurrent reads/writes to group states are safe
  • File persistence doesn't corrupt state.json
  • Statistics counters remain consistent

🎯 Common Use Cases

Use Case 1: First-Time Message Processing

# Message arrives for the first time
if not state.is_seen(group, msg_id):     # Returns False
    state.mark_seen(group, msg_id)        # Persist to disk
    # Process message...
    if matcher.matches(text):
        state.match_count += 1
        if not state.is_reacted(group, msg_id):
            success = await _react(element)
            if success:
                state.reaction_count += 1
                state.mark_reacted(group, msg_id)  # Persist to disk

Use Case 2: Duplicate Message (Already Seen)

# Same message appears again
if not state.is_seen(group, msg_id):     # Returns True (already seen)
    # Skip entirely - no processing

Use Case 3: Message Match But Already Reacted

# Message matches pattern but was reacted in previous run
if matcher.matches(text):
    if state.is_reacted(group, msg_id):  # Returns True
        log("已点赞")  # Skip reaction
        continue
